## 1. Verdict

Both attack vectors from the assignment are **closed and demonstrated live**:

- **Vector A — hijack a bot/other PR branch, then self-approve:** blocked. A
  write-access developer cannot push onto the bot's PR branch or create a branch
  in the bot namespace (S4, S5), and `require_last_push_approval` +
  `dismiss_stale_reviews_on_push` defeat self-approval-via-non-authorship (C4).
- **Vector B — sockpuppet fork PR, self-approved:** blocked. A fork PR requires
  2 write-access approvals excluding the author and head-pusher (S3), and the
  required status check is pinned to the gatekeeper App so a forged status
  cannot satisfy it (S9).

The bot exemption requested (bots work without 2 approvals) is live and correct:
bot PRs now take the single-approval four-eyes path (S2) while fork PRs remain at
2 (S3) and internal write-user PRs stay at 1 (S1).

Residual gaps and items needing a second reviewer identity to fully exercise are
in §5.

## 6. Residual gaps & recommendations

1. **Review-approval paths not live-exercised.** `dismiss_stale_reviews_on_push`,
   `require_last_push_approval`, and the **success** side of the fork 2-approval
   gate (two valid write approvals actually merging) need two write-access
   reviewer accounts with API tokens — unavailable in this harness. *Recommend a
   manual test with two real reviewers:* approve a PR, push a new commit, confirm
   the approval is dismissed; and approve a fork PR with two write users, confirm
   it becomes mergeable.
2. **Bot-exemption trust anchor.** `origin-policy` trusts a same-repo head under
   `poc-ci-bot/**` because the namespace ruleset blocks human writes there. This
   is only as strong as that ruleset staying `active` with no bypass actors. If a
   bot namespace ruleset were ever disabled or given a bypass actor, the
   exemption would trust an unlocked namespace. *Recommend:* alert on
   `repository_ruleset.update` for the bot namespaces (the audit collector +
   Wazuh rules already target this), and keep `BOT_BRANCH_PREFIXES` in sync with
   the terraform `bot_namespaces`.
3. **`can_admins_bypass: true` on environments.** Applies to *deployment*
   approvals, not merges — an admin could self-approve a deployment to
   `bot-automation`/`origin-policy`, not bypass four-eyes. Low risk; note for
   completeness. Consider setting it false if deployment approvals become
   security-relevant.
4. **Fork gate vs repo visibility.** `arrakis` is currently **private**, yet an
   external fork exists (`54m-sep10l/arrakis`) and `allow_forking` is false at the
   repo. The fork gate is designed for the open-source scenario named in the
   assignment ("opening forks to open-source repositories"). *Recommend* auditing
   how the existing private-repo fork exists (pre-existing / outside-collaborator)
   and confirming the gate before the repo is made public.
5. **Org-wide SHA pinning.** Workflows pin actions by SHA and the org uses a
   `selected` actions allowlist, but `sha_pinning_required` was `false` org-wide
   in the last TF state. *Recommend* enabling org SHA-pinning as defense-in-depth.
6. **Internal non-write, non-bot PR path.** The classifier routes this to the
   2-approval gate (defensive), but it could not be produced live (creating a
   same-repo branch requires write or the bot). Covered by unit tests of the
   decision tree only.
7. **Stale PRs.** #2 (bot heartbeat → `main`, old workflow) and #17 (older Sam
   fork PR predating enforcement) should be closed or re-triggered.
